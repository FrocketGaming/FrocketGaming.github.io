## Deep Dive: Polars 2.0

Polars 2.0 shipped on October 6. Back in Issue 1, Polars was the first package I reviewed, and the lazy API was the part I said was worth learning first. That is the part that changed the most in 2.0. Every `LazyFrame` now runs on the new streaming engine by default, and a handful of older behaviors were removed or tightened.

Most of the upgrade is good news: it's faster, it uses less memory, and more mistakes raise errors instead of being guessed at. The catch is that some changes give you different results without any error. So this deep dive covers the new features first, then the changes you need to look for before you bump the version.

Every example below was run against `polars==2.0.0`.

### Streaming is the default engine
In 1.x, `.collect()` ran your query on the in-memory engine unless you asked for streaming. In 2.0 it is the other way around. Streaming processes data in batches across all your cores, so most queries get faster and use less memory without any code changes.

The tradeoff is row order. To go fast, the streaming engine does not promise to keep rows in their original order for operations like `group_by`, `join`, and `unpivot`.

```python
import polars as pl

lf = pl.LazyFrame({"k": [i % 1000 for i in range(200_000)], "v": range(200_000)})

lf.group_by("k").agg(pl.col("v").sum()).collect()["k"].head(5).to_list()
# [222, 232, 79, 101, 117]  <- different every run

lf.group_by("k", maintain_order=True).agg(pl.col("v").sum()).collect()["k"].head(5).to_list()
# [0, 1, 2, 3, 4]
```

Joins take a string that tells Polars which side's order to keep:

```python
left.join(right, on="id", maintain_order="left")
```

If what you need is a specific order, a `.sort()` at the end says so explicitly and is the safest fix. Use `maintain_order` when you want the original input order.

If you need time to migrate, you can switch back to the old engine for a whole session:

```python
pl.Config.set_engine_affinity("in-memory")
```

or set `POLARS_ENGINE_AFFINITY=in-memory` as an environment variable. I'd use this to compare outputs during the upgrade, not as a permanent setting.

### Spilling to disk
2.0 also includes the first version of out-of-core support. When a query's memory use reaches about 80% of your RAM, Polars starts spilling to disk (up to 64 GB by default) instead of crashing. It's on by default, so there is nothing to configure.

Before you plan around it, know the limits. Sorts, window functions, and many expressions can spill today. **Joins and group-bys cannot yet.** The Polars team says those are on the roadmap. If your big query is a large join, it still has to fit in memory.

### The new `Map` dtype
Dictionary-shaped data used to show up as `List(Struct({"key", "value"}))`, and you had to unpack it yourself. In 2.0 it is a real `pl.Map` type with its own `.map` namespace.

```python
df = pl.DataFrame(
    {
        "user": ["alice", "bob", "carol"],
        "scores": pl.Series(
            [{"math": 90, "art": 75}, {"math": 60}, {}],
            dtype=pl.Map(pl.String, pl.Int64),
        ),
        "subject": ["art", "art", "math"],
    }
)

df.select(
    "user",
    pl.col("scores").map.get("math").alias("math"),
    pl.col("scores").map.get(pl.col("subject")).alias("by_subject"),
    pl.col("scores").map.contains_key("art").alias("has_art"),
    pl.col("scores").map.len().alias("n"),
    pl.col("scores").map.keys().alias("keys"),
)
```

```
┌───────┬──────┬────────────┬─────────┬─────┬─────────────────┐
│ user  ┆ math ┆ by_subject ┆ has_art ┆ n   ┆ keys            │
╞═══════╪══════╪════════════╪═════════╪═════╪═════════════════╡
│ alice ┆ 90   ┆ 75         ┆ true    ┆ 2   ┆ ["math", "art"] │
│ bob   ┆ 60   ┆ null       ┆ false   ┆ 1   ┆ ["math"]        │
│ carol ┆ null ┆ null       ┆ false   ┆ 0   ┆ []              │
└───────┴──────┴────────────┴─────────┴─────┴─────────────────┘
```

`map.get()` can take a column as well as a literal, so each row can look up a different key. That's the `by_subject` column above, and it's the one I'd have reached for `map_elements` to do before. A missing key comes back as `null` instead of raising an error.

**Note**: Map columns in Parquet, Arrow, and Iceberg files now load as `Map` too. If you have code that treated them as a list of key/value structs, `.map.entries()` gives you that shape back. `to_list()` now returns plain Python dicts.

### SQL is a first-class citizen
Polars has had a SQL interface for a while, but 2.0 is where the team calls it first-class. The optimizer gained join reordering, better common-subplan elimination, and dynamic predicates with bloom filters, mostly to make SQL-shaped queries run well. You can query DataFrames in your session by variable name, the same trick I showed with DuckDB in Issue 1:

```python
sales = pl.DataFrame({"region": ["e", "w", "e"], "amount": [10, 20, 30]})

pl.sql("""
    select region, sum(amount) as total
    from sales
    group by region
    order by total desc
""").collect()

# or on one frame, where it's called self
sales.sql("select region, count(*) as n from self group by region")
```

`pl.sql` returns a `LazyFrame`, so it goes through the same optimizer as expression code. I'd still write most things as expressions, but I don't think you need to switch to DuckDB just because a query is easier to express in SQL anymore.

### Stricter by default
The general direction of 2.0 is to fail early instead of quietly coercing types. Two examples I hit right away:

```python
pl.Series([1]).is_in([1.99])
# InvalidOperationError: 'is_in' cannot check for Int64 values in List(Float64) data.
# (1.x coerced both sides to Float64 and returned false)

pl.Series(["2026-10-19"]).cast(pl.Date)
# InvalidOperationError: casting from string to date is not supported.
# It was removed in Polars 2.0. Use `str.to_date()` instead.
```

Polars puts the fix right in the error message, which makes this kind of change easy to deal with.

The best tool for this is `collect_schema()`. It resolves every column's type through the whole plan without reading any data, so a type mismatch fails in milliseconds instead of halfway through a long job:

```python
lf = pl.LazyFrame({"price": ["10.5", "3"], "qty": [1, 2]})

lf.with_columns((pl.col("price") * pl.col("qty")).alias("total")).collect_schema()
# InvalidOperationError: arithmetic on dtypes str and i64 is not allowed
# (lhs: column 'price', rhs: column 'qty'); try an explicit cast first
#
# Resolved plan until failure:
#   ---> FAILED HERE RESOLVING 'with_columns' failed <-
```

I'd make this the first line of any pipeline test.

### Changes that don't raise errors
These are the ones worth reading twice. Your code runs, but the output changes.

**`explode()` drops empty lists.** An empty list used to become a `null` row. Now it becomes no row.

```python
df = pl.DataFrame({"a": [[1], []]})

df.explode("a")                      # 1 row:  [1]
df.explode("a", empty_as_null=True)  # 2 rows: [1, null]  (the 1.x behavior)
```

**Signed int + `UInt64` is now `Int128`.** It used to be `Float64`, which loses precision on large values. The new result is exact, but the dtype changes, so a downstream schema check or database write can break.

**Selectors combined with expressions.** `cs.integer() & pl.col("mask")` used to mean "the integer columns that are also `mask`". Now it does a bitwise AND of `mask` with every integer column.

```python
import polars.selectors as cs

df = pl.DataFrame({"a": [1, 2], "b": [3, 4], "mask": [1, 0]})

df.select(cs.integer() & pl.col("mask"))      # a, b, mask, all AND-ed with mask
df.select(cs.integer() & cs.by_name("mask"))  # just mask, the 1.x meaning
```

If you meant column selection, keep both sides as selectors.

**`pl.datetime()` takes its name from its first argument.** This one can overwrite data inside `with_columns`:

```python
df = pl.DataFrame({"year": [2026], "month": [10], "day": [19]})

df.with_columns(pl.datetime("year", "month", "day"))
# the "year" column is now a datetime

df.with_columns(pl.datetime("year", "month", "day").alias("dt"))
# what you wanted
```

`pl.repeat()` follows the same rule. An `.alias()` fixes both.

**`scan_csv` infers the schema from the first 10 files.** If you scan a folder of CSVs and a later file has different types, it can now fail. Pass `infer_schema_files=` if you need it to look at more files.

### Changes that do raise errors
These are easier to deal with because the error points you at the problem:

- `pl.concat(how="horizontal")` raises when the frames have different heights. Use `how="horizontal_extend"` to pad with nulls like before.
- File-like objects are no longer rewound for you. If you write Parquet to a `BytesIO` and read it back, call `buf.seek(0)` first.
- `with_row_count()` is gone. Use `with_row_index()`, and note its default column name is `"index"`, not `"row_nr"`.
- `LazyFrame.profile()` and `read_ipc(..., memory_map=..., rechunk=...)` were removed.

The upgrade guide has the full list.

### How I'd upgrade
1. Pin it in a branch: `uv add "polars>=2,<3"`.
2. Run your tests and fix whatever raises. The error messages usually name the replacement.
3. For the changes that don't raise, run your main pipelines on both engines and compare. `pl.Config.set_engine_affinity("in-memory")` gives you the old engine on 2.0. Sort both outputs before comparing so row order doesn't show up as a false difference.
4. Search your code for `explode(`, `pl.datetime(`, `selectors`, and any `group_by` or `join` whose output order you rely on.
5. Once the outputs match, remove the engine override.

### About those benchmarks
The release post says Polars leads DuckDB and DataFusion on TPC-H and TPC-DS-derived queries. On large data (scale factor 100) and big machines, that holds. Going from 16 to 192 cores, Polars sped up 3.8x on TPC-H, compared to 3.2x for DuckDB 1.5.6.

On smaller data the picture is less clear. At scale factor 10, extra cores don't help default Polars, and DuckDB 1.5.6 was 1.8x faster on TPC-H and 1.3x faster on TPC-DS. The team says they've found the per-thread overhead behind this and plan to fix it. They also ran these benchmarks themselves, so take them as a strong claim rather than a final verdict. For most of us, the fact that Polars and DuckDB are this close is the real takeaway. Pick whichever one you find easier to write.
