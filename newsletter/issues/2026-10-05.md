This issue will deep dive into `zbq` or `lazy bigquery` which is a package I wrote a few years ago that I've been slowly improving on. The aim was to make interacting with BigQuery and GCS simpler. You'll notice that the majority of this issue is simply the deep dive, so I hope you enjoy!

## BigQuery Cost Habits

A short list of habits that keep a BigQuery bill predictable. Most of them show up somewhere in the zbq walkthrough later in this issue.

- **Avoid `select *` on wide tables.** BigQuery bills by bytes scanned per column, not per row, so pulling every column when you need three is often the single biggest line on a bill. `select col_a, col_b, col_c` instead of `select *` can be the difference between scanning megabytes and gigabytes on the same table.
- **Partition and cluster your tables.** A query filtered on `where order_date >= @start` only scans the partitions it touches if the table is partitioned on that column; on an unpartitioned table it scans everything regardless of the filter. zbq's write() doesn't support setting these yet, but it's planned - see "Partition and cluster on create" later in this issue.
- **Reach for `.preview()` before `limit`.** `select * from table limit 10` still scans the whole table unless it's already filtered down by partitioning or clustering. `.preview()` reads rows straight from table storage instead of running a query, so it costs nothing no matter how large the table is.
- **Dry run before running.** `.dry_run()` reports bytes processed for free. Wiring the check into a script - `if info.total_bytes_processed > threshold: raise RuntimeError(...)` - catches a runaway query before it runs, not after the bill shows up.
- **Cap bytes billed per query.** BigQuery lets you set a maximum bytes billed on a job, so a query that would scan far more than expected fails immediately with a clear error instead of quietly running to completion.

## Package Reviews

### pandera

A schema validation library for dataframes, with native support for Polars (as well as pandas and pyarrow). You define what a dataframe should look like - column names, types, nullability, even value constraints - and pandera checks a dataframe against that schema, raising with exactly which column and rows failed.

It pairs well with the schema evolution feature planned for zbq (see "What's Next for zbq," later in this issue): validating a dataframe's shape before calling `write()` catches a bad column or type before it reaches BigQuery as a failed load job.

#### Example

```python
import polars as pl
import pandera.polars as pa

class OrderSchema(pa.DataFrameModel):
    order_id: int
    customer_id: int
    amount: float = pa.Field(ge=0)
    status: str = pa.Field(isin=["pending", "shipped", "delivered"])

df = pl.DataFrame({
    "order_id": [1, 2],
    "customer_id": [100, 101],
    "amount": [29.99, -5.00],
    "status": ["shipped", "delivered"],
})

OrderSchema.validate(df)
# raises SchemaError: amount has a value below the allowed minimum (row 1)
```

- [Read more about pandera](https://pandera.readthedocs.io/)

## New to Python?

Two small concepts that show up in the zbq examples below, if either one didn't quite click.

### The `with` statement and context managers

`with` guarantees a cleanup step runs when a block ends, even if something inside it raises an exception. Here's the context manager example from later in this issue:

```python
with zc as client:
    df1 = client.read("SELECT * FROM `project.dataset.table1`")
    df2 = client.read("SELECT * FROM `project.dataset.table2`")
    result = client.write(df1, "project.dataset.output_table")
# client is cleaned up here, even if one of the calls above had raised
```

Anything usable with `with` defines two methods: `__enter__`, which runs when the block starts (and can hand back an object - `client`, above), and `__exit__`, which runs when the block ends, exception or not. A plain function can't guarantee an "afterward" step runs on every possible exit path; a context manager can.

The same pattern shows up constantly outside zbq, too:

```python
with open("data.csv") as f:
    contents = f.read()
# file is closed here, even if .read() had thrown
```

- [Read more about context managers](https://docs.python.org/3/reference/datamodel.html#context-managers)

### Running things at the same time with `asyncio.gather()`

Regular Python runs one line at a time, so a slow network call just blocks everything else until it returns. `async`/`await` lets you say "start this, and let other work happen while it's in flight." Here's the async example from later in this issue:

```python
sales, users = await asyncio.gather(
    azc.read("select * from `project.dataset.sales`"),
    azc.read("select * from `project.dataset.users`"),
)
```

Both queries go out essentially at once instead of waiting for the first to finish before starting the second. `asyncio.gather()` takes any number of `async def` calls (coroutines), runs them concurrently, and returns their results in the same order you passed them in - here as a tuple, unpacked straight into `sales` and `users`.

The catch: everything has to be `async` end to end. `await` only works inside a function defined with `async def`, and that function has to be kicked off with something like `asyncio.run(main())`. You can't sprinkle `await` into ordinary code.

- [Read more about asyncio.gather()](https://docs.python.org/3/library/asyncio-task.html#asyncio.gather)

## Deep Dive: zbq
Recently I released the 2.0 and 2.1 versions of this package so it feels appropriate to review it because the 2.1 release had some breaking changes to earlier versions.

zbq (Lazy BigQuery) is a GCP wrapper for BigQuery and Google Cloud Storage. I created this to simplify the syntax for basic tasks as well as parameters, read, write, async etc.

It natively returns data as a polars dataframe but thanks to the polars api, you can adjust this to a pandas dataframe very simply.

### Getting Set Up
zbq needs Python 3.11 or newer. Install it with uv:
```
uv add zbq
```

zbq uses your Google Application Default Credentials, so if you've already logged in with the gcloud CLI there's nothing else to configure:
```
gcloud auth application-default login
```

The project is picked up automatically. zbq uses the first one of these it finds:
1. A project you pass in code: `BigQueryHandler(project_id="my-project")`
2. The `GOOGLE_CLOUD_PROJECT` environment variable
3. Your active gcloud configuration (the same project `gcloud config get-value project` shows)

The environment variable comes before gcloud config, the same as Google's own libraries. That makes it easy to point a CI job or a container at a different project without touching gcloud. If you switch between gcloud configurations (`gcloud config configurations activate work`), zbq follows along.

You can check or change the project at any time:
```python
from zbq import zclient as zc

print(zc.project_id)
zc.project_id = "my-other-project"
```

**Note**: `zclient` picks its project when you import zbq, so set `GOOGLE_CLOUD_PROJECT` before starting Python. Setting it from inside Python only affects clients you create after that.

If there are no credentials, zbq raises a `ZbqAuthenticationError` that tells you the exact command to run, instead of a long Google auth traceback.

### Basic Read from BigQuery
```python
from zbq import zclient as zc
import polars as pl

df: pl.DataFrame = zc.read("select * from `project.dataset.table`")

# Pandas version
df = zc.read("select * from `project.dataset.table`").to_pandas()

# Reading with Parameters
df: pl.DataFrame = zc.read(
    "select * from `project.dataset.table` where region = @region and active = @active",
    parameters={"region": "US", "active": True}
)
```

### Parameters In Depth
Parameters are one of the main reasons I wrote zbq. With the Google client you have to build a `QueryJobConfig` and wrap every value in a `ScalarQueryParameter` with its BigQuery type spelled out. With zbq you pass a normal Python dict and it works out the types for you:

| Python value | BigQuery type |
|--------------|---------------|
| `str` | `STRING` |
| `int` | `INT64` |
| `float` | `FLOAT64` |
| `bool` | `BOOL` |
| `datetime` | `TIMESTAMP` |
| `date` | `DATE` |
| `None` | `STRING` (NULL) |
| `list` / `tuple` | `ARRAY<...>` based on the first non-null value |

These are sent to BigQuery as real query parameters, not pasted into the SQL text. That means a value like `"'; DROP TABLE users; --"` is just treated as a string, so SQL injection isn't possible through parameters.

Lists are great for `IN` filters. Use them with `UNNEST`:
```python
from datetime import date

df = zc.read(
    """
    select * from `project.dataset.orders`
    where order_date >= @start
    and status in unnest(@statuses)
    """,
    parameters={"start": date(2026, 1, 1), "statuses": ["shipped", "delivered"]}
)
```

**Note**: A Python `datetime` becomes a `TIMESTAMP`. If you're comparing against a `DATETIME` column, cast it in the query (e.g. `datetime(@ts)`) or BigQuery will complain about mismatched types.

Table names are the one thing BigQuery won't let you parameterize. zbq handles this with two special parameter names, `table` and `table_name`. zbq checks that the value looks like `project.dataset.table` (letters, numbers, dashes, underscores and dots only), wraps it in backticks, and puts it in the query:
```python
df = zc.read(
    "select * from @table where region = @region",
    parameters={"table": "project.dataset.hotels", "region": "US"}
)
```

### Dry Runs
Before running a query you can do a dry run with `.dry_run()`. This shows you the final query with your parameters filled in, validates it against BigQuery, and tells you how much data it would process, without actually running it.
```python
from zbq import zclient as zc

info = zc.dry_run(
    "select * from `project.dataset.table` where region = @region",
    parameters={"region": "US"}
)

# Example Output of Dry Run

# Output:
# DRY RUN - Query that would be executed:
# --------------------------------------------------
# select * from `project.dataset.table` where region = 'US'
# --------------------------------------------------
# Parameters substituted above:
#   @region (STRING): 'US'
# --------------------------------------------------
# Bytes that would be processed: x.xx MB
# (Actual cost depends on your pricing model/edition and region.)
# --------------------------------------------------
```

The printed query with the values filled in is only for you to read. The real query still goes to BigQuery with proper parameters. It's handy when a query returns nothing and you want to see exactly what was filtered on.

`.dry_run()` also returns the same information, so you can use it in scripts. For example, stopping a job if a query would scan too much data:
```python
if info.total_bytes_processed > 10 * 1024**3:  # 10 GB
    raise RuntimeError("This query would scan too much data")

print(info.statement_type)     # "SELECT"
print(info.referenced_tables)  # ["project.dataset.table"]
```

If the query has a mistake (bad column name, missing table etc.), the dry run prints the query and then raises BigQuery's error, so you find out before paying for anything.

### Read Only
`.read()` is really meant only for reading data, so it is always read only. When you run a `.read()`, it first sends the query to BigQuery to validate that it is a `SELECT` type. If it isn't, then it will raise an error. There's no flag to turn this off; anything that changes data goes through `.execute()` instead (more on that below).

**Note**: This validation check with BigQuery is free in terms of data cost but does add another trip to BigQuery before running the query.

This code below would result in an error:
```python
zc.read("delete from `project.dataset.table` where true")

# Error Example
"""
zbq.base.ZbqOperationError: read() is read-only and refused a DELETE statement. Use execute() to modify data.
"""
```

#### How it decides what's a SELECT
The simple way to build this would be to scan the SQL for words like `DELETE` or `UPDATE`. I originally did something like that, and it broke on queries like this:
```sql
with HtlsToUpdate as (
    select * from `project.dataset.hotels` where needs_refresh
)
select * from HtlsToUpdate
```
That's a plain `SELECT`, but the CTE name has "Update" in it. Text matching also misses things like comments and string values that contain those words.

So zbq doesn't read the SQL text at all. It runs a free dry run and asks BigQuery what kind of statement the query is. BigQuery has already parsed it properly, so:
- CTEs, subqueries, and `INFORMATION_SCHEMA` queries are allowed
- `INSERT`, `UPDATE`, `DELETE`, `MERGE`, DDL, `CALL`, and `EXPORT DATA` are refused, even when they use a CTE
- Scripts (anything with `DECLARE`, `SET`, or several statements separated by `;`) are refused, even if they only read. Use `.execute(..., return_dataframe=True)` for those
- A typo in the SQL fails at the check with the same error the real run would give

If you're running SQL you didn't write yourself (user input, an LLM, an MCP tool), I'd still pair this with credentials that only have the BigQuery Data Viewer and Job User roles. Then even a query that somehow got past zbq couldn't write anything.

### Previewing and Exploring
If you just want to see what's in a table, use `.preview()`. It doesn't run a query at all; it reads rows straight from the table storage, so it scans no bytes and costs nothing even on a huge table. A `select * ... limit 10` can still scan the whole table and charge for it.
```python
sample = zc.preview("project.dataset.big_table", max_results=10)
```

There are also helpers for finding your way around. Each one returns a polars dataframe:
```python
zc.list_projects()                  # project_id, friendly_name
zc.list_datasets()                  # datasets in the current project
zc.list_tables("my_dataset")        # table_id, table_type for one dataset

# Every table in every dataset of the current project
tables = zc.catalog()

# Or across every project your credentials can see
tables = zc.catalog(all_projects=True)
```

`catalog()` makes one API call per dataset, so it can be slow on big projects. The async version (below) runs those calls at the same time.

### Basic Write to BigQuery
Writing is pretty simple, just use `write()`.

This code will append data from a dataframe to a table.
```python
from zbq import zclient as zc

zc.write(
    df=df,
    full_table_path="project.dataset.table"
)
```

What if the table doesn't exist? `create_if_needed` is `True` by default, so if the table doesn't exist it will create it first, otherwise it continues to append data. If you'd rather it fail when the table is missing, pass `create_if_needed=False`.
```python
from zbq import zclient as zc

zc.write(
    df=df,
    full_table_path="project.dataset.table",
    create_if_needed=False
)
```

What if you want to replace the data every time? Use `write_type="truncate"` (the default is `append`). Since this wipes out what's already in the table, you have to confirm it with `confirm=True`, otherwise zbq raises an error before anything is uploaded.
```python
from zbq import zclient as zc

zc.write(
    df=df,
    full_table_path="project.dataset.table",
    write_type="truncate",
    confirm=True
)
```

**Note**: `write_type` only accepts `"append"` or `"truncate"`. A typo like `"truncat"` raises an error instead of quietly appending.

#### How writes work
Under the hood, `write()` saves your dataframe to a temporary Parquet file and sends it to BigQuery as a load job. A couple of nice side effects:
- Parquet keeps your column types, so dates stay dates and integers stay integers. With CSV, BigQuery has to guess the types.
- Load jobs don't have the query costs you'd get from `INSERT` statements.
- When `create_if_needed` creates a new table, the schema comes straight from your dataframe.

The temp file is always deleted afterwards, even if the load fails.

### Inserts, Updates, Deletes
Anything that changes data goes through `.execute()`. It covers inserts, updates, and deletes, as well as other use cases like Merge, DDL, Scripts etc.
```python
from zbq import zclient as zc

zc.execute(
    "INSERT INTO @table_name (col1, col2) VALUES (@val1, @val2)",
    parameters={"table_name": "project.dataset.table", "val1": "data", "val2": 123}
)
zc.execute(
    "UPDATE @table_name SET col = @new_value WHERE id = @target_id",
    parameters={"table_name": "project.dataset.table", "new_value": "updated", "target_id": 1}
)
zc.execute(
    "DELETE FROM @table_name WHERE id IN UNNEST(@ids)",
    parameters={"table_name": "project.dataset.table", "ids": [1, 2, 3]}
)
```

`.execute()` returns a result with details about the job, including how many rows were changed:
```python
result = zc.execute(
    "DELETE FROM @table_name WHERE id IN UNNEST(@ids)",
    parameters={"table_name": "project.dataset.table", "ids": [1, 2, 3]}
)

print(result.num_dml_affected_rows)  # 3
print(result.statement_type)         # "DELETE"
print(result.total_bytes_processed)
print(result.job_id)
```

Originally, I created `insert(), delete(), and update()` for this. They still exist if you prefer them, but they are just aliases for `.execute()`, so they don't check that the query matches the method name.
```python
from zbq import zclient as zc

zc.insert(
    "INSERT INTO @table_name (col1, col2) VALUES (@val1, @val2)",
    parameters={"table_name": "project.dataset.table", "val1": "data", "val2": 123}
)
```

Other DML and DDL operations can be done with `.execute()` too.
```python
from zbq import zclient as zc

zc.execute("""
    CREATE TEMP TABLE staged AS
    SELECT * FROM `project.dataset.incoming` WHERE region = @region;

    MERGE `project.dataset.target` T
    USING staged S ON T.id = S.id
    WHEN MATCHED THEN UPDATE SET T.value = S.value
    WHEN NOT MATCHED THEN INSERT (id, value) VALUES (S.id, S.value);
""", parameters={"region": "US"})  # Returns job details by default
```

If a statement returns rows (like a stored procedure or a script ending in a `SELECT`), use the `return_dataframe=True` flag to get them back as a dataframe.
```python
from zbq import zclient as zc
import polars as pl

df: pl.DataFrame = zc.execute("CALL `project.dataset.my_procedure`()", return_dataframe=True)
```

### Timeouts
Every call has a timeout, 300 seconds by default. You can change it per call or for a whole client:
```python
from zbq import BigQueryHandler

# One slow query
df = zc.read("select * from `project.dataset.huge_table`", timeout=1800)

# A client where everything gets 20 minutes
long_client = BigQueryHandler(default_timeout=1200)
```

For `.read()`, the timeout covers the whole call: the read-only check, waiting for the query, and downloading the rows all share the same time limit. So `timeout=60` really means about 60 seconds. It doesn't give each step its own 60 seconds. When time runs out you get a normal Python `TimeoutError`.

### Async
Every zbq call waits until BigQuery answers. That's fine in a script, but inside an async app (FastAPI, an MCP server etc.) one slow query would freeze everything else. For that there's `azclient`, which has the same methods as `zclient` but as `async` functions:
```python
import asyncio
from zbq import azclient as azc

async def main():
    # Run several queries at the same time
    sales, users = await asyncio.gather(
        azc.read("select * from `project.dataset.sales`"),
        azc.read("select * from `project.dataset.users`"),
    )

    # Same methods as zclient
    await azc.execute("CALL `project.dataset.refresh`()")

    # catalog() lists datasets and tables at the same time instead of one by one
    tables = await azc.catalog()

asyncio.run(main())
```

Google's BigQuery library doesn't have an async version, so each call runs on a background thread. That still gives real speed-ups, because most of the time is spent waiting on BigQuery rather than using the CPU. By default up to 8 calls run at once, and any extra calls wait their turn. If you need a different limit, create your own async client:
```python
from zbq import AsyncBigQueryHandler

async with AsyncBigQueryHandler(max_concurrency=16) as aclient:
    df = await aclient.read("select 1")
```

`azclient` shares its project, credentials, and settings with `zclient`, so changing `zc.project_id` changes both.

### Google Cloud Storage
The other half of zbq is `zstorage`, for Google Cloud Storage. The bucket path is just `"bucket"` or `"bucket/folder/subfolder"`.

Uploading a single file or a whole folder:
```python
from zbq import zstorage

zstorage.upload_file("./report.csv", "my-bucket/reports")

# Upload every CSV in a folder, skipping temp files
result = zstorage.upload(
    "./exports",
    "my-bucket/exports",
    include_patterns="*.csv",
    exclude_patterns="temp_*",
)
print(f"{result.uploaded_files}/{result.total_files} files, {result.total_bytes:,} bytes")
```

Downloading works the same way, and there's a shortcut for grabbing just the newest matching file:
```python
zstorage.download("my-bucket/exports", "./data", include_patterns="*.parquet")

zstorage.download_latest("my-bucket/backups", "./restore", include_patterns="*.zip")
```

Folder uploads and downloads run in parallel with a progress bar, and failed files are retried automatically. The result tells you what happened instead of stopping at the first error. Check `result.failed_files` and `result.errors` afterwards. Pass `dry_run=True` to see what would be transferred without transferring anything.

My favorite part is reading files straight into a dataframe without downloading them first:
```python
# Every parquet file in a folder, combined into one dataframe
df = zstorage.read("my-bucket/sales/2026", include_patterns="*.parquet")

# Add a column showing which file each row came from
df = zstorage.read("my-bucket/sales/2026", include_patterns="*.csv", add_source_column=True)

# Or one file at a time, if they're too big to hold together
for filename, file_df in zstorage.read_iter("my-bucket/logs", include_patterns="*.ndjson"):
    print(filename, file_df.height)
```

If the files don't all have the same columns, `read()` still combines them and fills the missing columns with nulls. CSV, Parquet, JSON, and NDJSON are detected from the file extension.

Put together, going from files in GCS to a BigQuery table is only a few lines:
```python
import polars as pl
from zbq import zclient as zc, zstorage

orders = zstorage.read("my-bucket/orders/2026-10", include_patterns="*.csv")
active = orders.filter(pl.col("status") == "active")
zc.write(active, "project.dataset.active_orders", write_type="truncate", confirm=True)
```

### Errors
zbq has its own error types, so you can catch exactly what you care about:
```python
from zbq import ZbqAuthenticationError, ZbqConfigurationError, ZbqOperationError

try:
    df = zc.read("select * from `project.dataset.table`", timeout=60)
except ZbqAuthenticationError:
    ...  # no credentials - run gcloud auth application-default login
except ZbqConfigurationError:
    ...  # no project set
except ZbqOperationError:
    ...  # e.g. read() refused a non-SELECT, or a truncate without confirm=True
except TimeoutError:
    ...  # the call ran past its timeout
```

All three inherit from `ZbqError`, so `except ZbqError` catches any of them.

### Execution via Context Manager
zbq supports context manager as well:
```python
from zbq import zclient as zc

with zc as client:
    # Test query with a dry run first
    client.dry_run(
        "SELECT * FROM @table WHERE date >= @start_date",
        parameters={"table": "project.dataset.table1", "start_date": "2024-01-01"}
    )

    # Execute actual queries
    df1 = client.read(
        "SELECT * FROM @table WHERE date >= @start_date",
        parameters={"table": "project.dataset.table1", "start_date": "2024-01-01"}
    )
    df2 = client.read("SELECT * FROM `project.dataset.table2`")
    result = client.write(df1, "project.dataset.output_table")
```

### Logging
zbq logs with loguru, but it doesn't change your loguru setup. Its messages (like the dry run output) show up wherever your loguru logs already go. If you want zbq to be quiet:
```python
from loguru import logger

logger.disable("zbq")
```

### What's Next for zbq

Two features planned for a future release, both on `write()`. No release date on either yet — if you'd use one, let me know.

#### Schema evolution on append

Today, appending a dataframe with a column the table doesn't have just fails - the load job errors out immediately. BigQuery can handle this if you ask it to: new columns get added to the table, matched by name rather than position, and backfilled as `NULL` on the rows that already existed.

The plan is an opt-in flag:
```python
zc.write(
    df,
    "project.dataset.table",
    write_type="append",
    allow_schema_evolution=True,  # default False
)
```

Default `False`, for the same reason `write_type="truncate"` needs `confirm=True`: silent schema drift on an append shouldn't happen by accident. When it's on, zbq will log which columns got added. It only ever adds columns or loosens a `REQUIRED` column to `NULLABLE`; a type change, or a column that's really meant to replace another one, still fails. That's not evolution, that's a decision a person needs to make.

#### Partition and cluster on create

`create_if_needed=True` already builds a table from the dataframe's schema the first time you write to it, but there's no way to say how it should be partitioned or clustered, so every auto-created table starts out flat. The plan:
```python
zc.write(
    df,
    "project.dataset.table",
    partition_by="order_date",
    cluster_by=["region", "status"],
)
```

These only apply the first time a table is created - BigQuery doesn't let you change a table's partitioning or clustering columns afterward without rebuilding it, so passing them against a table that already exists will just be ignored, with a log line so it's not a silent no-op.
